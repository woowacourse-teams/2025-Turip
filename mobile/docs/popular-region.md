# 인기 관광지 지도 (feature/popularregion)

> 2026-09-10 작업 기록. 방문자 수 API 연동 + 실제 행정경계 지도 + 바텀시트 UX + **2층 지도(인기 관광지 14곳)** 까지 끝난 상태.

## 1. 지금까지 한 일

브랜치 `feature/#722` 에 커밋 3개로 나뉘어 있다. 모두 로컬에만 있고 푸시 전이다.

| 커밋 | 내용 |
|---|---|
| `bd4e45d65` | 방문자 수 API 연동, 목업 제거, 필터 제거 |
| `d32899023` | 보로노이 → 실제 시도 행정경계로 교체 |
| `f7e5ea643` | 바텀시트 전환 애니메이션 |

그 위에 **아직 커밋하지 않은 변경**이 있다. `GET /regions/popular-destinations` 를 붙여 지도를 2층으로 만든 작업이다.
아래층은 기존 시도 17개 그대로이고, 위층에 튜립 지역 카테고리 14곳(서울/부산/제주/인천/대전/대구/전주/강릉/속초/경주/공주/여수/수원/군산)을 덮어 그린다.
두 API 는 **둘 다 유지**한다.

작업 전 상태는 `stash@{4}` (2026-08-26) 에 남아 있다. 목업 데이터로 만든 화면 껍데기였고, 지금은 목업이 하나도 남아 있지 않다.

## 2. 데이터 흐름

```
GET /api/v1/regions/popularity            → 시도별 방문자 수 (아래층 색)
GET /api/v1/regions/popular-destinations  → 관광지 14곳 중 상위 10곳 + 순위 (위층 색)
GET /api/v1/contents?regionCategory=      → 시트 안 영상 카드 (지역 탭 시)
```

`region-categories` 는 이 화면에서 더 이상 쓰지 않는다. 지원 지역은 `popular-destinations` 의 후보 14곳이 곧 답이라
따로 교집합을 낼 이유가 없어졌다.

위층 API 는 좌표도 지역 코드도 주지 않고 **카테고리 이름만** 준다. 그래서 이름이 키다.

- `core/model` — `PopularDestination`, `DestinationVisitor`
- `core/data/dto/region` — `PopularDestinationResponse`, `DestinationVisitorResponse`
- `core/network/service/RegionService` — `getPopularDestinations()`
- `core/domain/repository/RegionRepository` — `loadPopularDestinations()`
- `core/data/repository/DefaultRegionRepository` — 시도 쪽과 같은 이유로 앱 수명 동안 캐시. 빈 응답은 캐시하지 않는다.

새로 추가한 레이어는 기존 Region 계통에 얹었다.

- `core/model` — `RegionPopularity`, `RegionVisitor`
- `core/data/dto/region` — `RegionPopularityResponse`, `RegionVisitorResponse`
- `core/network/service/RegionService` — `getRegionPopularity()`
- `core/domain/repository/RegionRepository` — `loadRegionPopularity()`
- `core/data/repository/DefaultRegionRepository` — 앱 수명 동안 캐시. **빈 응답은 캐시하지 않아** 서버가 채워지면 다음 진입에 반영된다.

## 3. 지도가 그려지는 방식

### 두 층

`RegionShapeKey` 가 층을 가른다. `Sido(areaCode)` 는 `KoreaRegionShapes`, `Destination(이름)` 은 `PopularDestinationShapes` 에서 경계를 찾는다.
선택 식별자(`code`)는 `sido:41`, `dest:수원` 처럼 접두사를 붙인 문자열이라 시트·선택 로직은 예전 그대로다.

- 14곳 중 **6곳(서울·부산·대구·인천·대전·제주)은 시도 하나가 통째로 그 지역**이다. 경계를 새로 갖지 않고 시도 것을 그대로 쓴다.
  같은 땅을 두 번 그리지 않도록 **그 6개 시도는 아래층에서 뺀다.** 두 API 의 숫자가 다르면 위층 값이 보인다.
- 나머지 8곳만 시군구 경계를 따로 갖는다. 총 2.9KB, 352점.
- **정규화는 층마다 따로** 한다. 시도(수백만)와 관광지(수십만)를 한 자로 재면 속초 같은 작은 시가 늘 가장 옅게 나온다.
- **색 띠는 두 층이 같다.** 한때 아래층을 회색 띠로 빼 봤지만 되돌렸다.
  대신 **두 층의 색을 값으로 비교하면 안 된다.** 층마다 따로 정규화하므로 서울(1위 관광지, 2847만)과
  경기(배경 시도, 950만)가 둘 다 `intensity 1.0` 이라 **같은 진한 빨강**이 된다.
  둘을 가르는 건 색이 아니라 흰 경계선뿐이다. 층을 눈에 띄게 갈라야 하면 관광지 테두리를 굵게/진하게 하는 쪽이
  색을 건드리지 않는 방법이다.
- 그리기/탭 순서 규칙은 손대지 않았다. 관광지는 언제나 자기 시도보다 좁으므로 **넓은 것부터 칠하고 좁은 것부터 탭 판정**하는 기존 한 가지 규칙으로 두 층이 함께 정렬된다.
- 상위 10곳만 내려오므로 **14곳 중 4곳은 위층에 안 뜬다.** 그때는 아래층 시도 색으로만 보인다.
- 위층 조회가 실패해도 지도는 그린다. 아래층만 남을 뿐이다.

### 상단 Top10 칩 줄

`PopularDestinationChipRow`. 앱바 바로 아래, 가로 스크롤. 순위 오름차순으로 관광지를 늘어놓는다.

지도만으로는 속초·수원처럼 작은 지역을 손가락으로 정확히 누르기 어려워서 만든 **두 번째 길**이다.
칩을 누르면 `SelectRegion` 을 그대로 보내므로 지도를 탭한 것과 완전히 같은 선택이 일어난다.
선택 상태의 단일 진실 공급원은 여전히 `selectedRegionCode` 하나다.

- 지도 위에 겹치지 않고 앱바 아래 자리를 차지한다. 지도에 얹으면 배지·범례와 자리를 다투고,
  시트가 올라올 때 같이 가려진다. 칩은 시트가 열려 있는 동안에도 눌러 지역을 바꿀 수 있어야 한다.
- 지도에서 고른 지역의 칩이 화면 밖이면 끌어온다. 단 **이미 온전히 보이는 칩은 건드리지 않는다.**
  누를 때마다 그 칩이 맨 앞으로 끌려오면 누른 자리가 움직여 옆 칩을 이어서 누르기 어렵다.

### 경계 데이터

`map/KoreaRegionShapes.kt` 에 통계청 2018년 시도 경계를 넣어 두었다. 29KB, 2,934점.

핵심은 **GeoJSON 이 아니라 TopoJSON 을 썼다**는 점이다. 폴리곤을 각각 단순화하면 맞닿은 경계가 서로 어긋나 지도에 실금 같은 틈이 생긴다. TopoJSON 의 공유 아크를 단순화하면 양쪽이 똑같이 줄어든다. 실측으로 틈이 73px → 40px (70만 px 중) 로 줄었고, 남은 것은 래스터화 반올림 수준이다.

- 원본: `southkorea/southkorea-maps` 의 `kostat/2018/json/skorea-provinces-2018-topo.json`
- 단순화: Douglas-Peucker, tol = 0.008도(화면 1dp 남짓), 최소 면적 0.003도²
- 좌표 형식: 1/10000도 정수를 **직전 점과의 차이**로 적은 문자열. 링은 `|`, 점은 공백, 위/경도는 `,`
- 다시 만들 일이 생기면 아래 4절 참고

### 그리는 규칙

- 값에 따라 지역을 통째로 칠하는 **단계구분도**. 예전의 방사형 blob 은 실제 경계와 따로 놀아서 버렸다.
- **넓은 지역부터 칠하고, 탭 판정은 좁은 지역부터** 본다. 경계 데이터에서 구멍을 걷어냈기 때문에 전남 링이 광주를 통째로 감싼다. 순서를 뒤집으면 광주를 영영 고를 수 없다.
  - 17개 시도를 전수 검사한 결과 이렇게 감싸이는 관계는 **광주 ⊂ 전남 한 쌍뿐**이다. (서울/경기, 대구/경북은 겹치지 않는다)
- 탭은 최근접 중심점이 아니라 **폴리곤 내부 판정**(광선 투사)이다.
- 라벨이 겹치면 **방문자 수가 많은 쪽이 이긴다**. 실제 응답 기준 `세종`만 대전에 밀린다.
- **방문자 수가 오기 전에도 지도 모양은 그린다.** 이때는 `UnknownLand`(회색)로 칠하고, 라벨을 붙이지 않고, 눌러도 반응하지 않는다. `HeatLow` 를 재활용하지 않은 이유는 *방문자가 적음* 과 *아직 모름* 이 다른 상태라서다.

### 성능

시트가 열릴 때 `bottomInset` 이 매 프레임 바뀐다. 그때마다 3천 점 합집합을 다시 만들면 끊기므로, **캔버스 크기가 그대로면 Path 를 재사용하고 배율·이동 변환만 적용**한다 (`RegionPathCache`, `KoreaMapProjection.transformTo`). 변환식은 6가지 inset 값에서 직접 투영과 대조해 오차 0을 확인했다.

## 4. 경계 데이터를 다시 만들어야 할 때

행정구역이 개편되면 이 작업이 필요하다. 파이프라인은 세션 스크래치패드에 있었고 재현 절차는 아래와 같다.

1. TopoJSON 내려받기 (위 URL)
2. arcs 를 델타 누적 + `transform` 적용해 위경도로 복원
3. **아크 단위로** Douglas-Peucker (링 단위로 하면 틈이 생긴다)
4. geometry 의 `arcs[0]`(외곽 링)만 사용, 구멍은 버린다 → 그래서 광주가 전남 안에 들어간다
5. 면적 하한으로 작은 섬 제거
6. KOSTAT 코드를 법정동 시도 코드로 변환 (`11→11, 21→26, 22→27, 23→28, 24→29, 25→30, 26→31, 29→36, 31→41, 32→51, 33→43, 34→44, 35→52, 36→46, 37→47, 38→48, 39→50`)
7. 델타 인코딩해 `ENCODED_SHAPES` 에 넣는다

주의: 백령도(인천)와 울릉도·독도(경북)는 `KoreaMapProjection` 의 경계 상자 밖이라 화면에 안 나온다. 데이터에는 들어 있다.

### 시군구 8곳은 절차가 조금 다르다

원본이 `skorea-municipalities-2018-topo.json` 이고, 시도와 **다른 파일**이라 단순화하면 해안선이 서로 어긋난다.
실측 최대 0.0079도(약 0.9km, 화면 1px)로 시도 경계 자체의 단순화 오차와 같은 수준이라 클리핑 없이 그냥 겹쳐 그린다.

시도 절차에서 두 군데를 바꿔야 한다.

1. **면적 하한을 그대로 쓰면 안 된다.** 시도용 0.003도² 는 수원시 구 하나(약 0.0025도²)보다 커서 본토가 통째로 잘린다.
   행정구역마다 **가장 큰 링은 무조건 남기고**, 섬에만 하한(0.0005도²)을 건다.
2. **아래층이 이미 버린 원해 섬은 위층에서도 빼야 한다.** 여수 거문도가 그런 경우로, 남기면 배경 없는 바다에 색점만 뜬다.
   링 중심이 부모 시도 안에 있을 때만 남기는 것으로 걸렀다.

수원시는 4개 구, 전주시는 2개 구로 쪼개져 있다. 구의 링을 그대로 담고 그리는 쪽에서 합집합을 내므로 구 경계는 안쪽에 남지 않는다.
KOSTAT 코드는 구 체계(경기 31, 강원 32, 충남 34, 전북 35, 전남 36, 경북 37)라 시도 코드와 다르다.

검증: 8곳 모두 **시청 좌표가 자기 폴리곤 안에** 들어가는 것으로 코드 매핑을 확인했다. 델타 인코딩 왕복도 확인했다.

## 5. 서버에 확인이 필요한 것

### 통합시 중복 (가장 시급)

실제 응답에 `12 전남광주통합특별시` 와 그 구성 지역인 `46 전라남도`, `29 광주광역시` 가 **함께** 내려온다. 스펙에는 17개라고 적혀 있는데 실제로는 18개다.

숫자도 맞지 않는다.

```
전남 2,113,740 + 광주 971,600 = 3,085,340
전남광주통합특별시              4,099,426   ← 더 큼
```

방문 인원수가 *외지인 + 외국인(현지인 제외)* 이라면, 두 지역을 통합할수록 서로 오가던 사람이 현지인으로 빠져 **합보다 작아져야** 한다. 중복 방문자가 한 번만 세어지는 것도 줄어드는 방향이다. 그런데 100만 명 더 많다.

**클라 임시 대응**: `SidoAreas.SUPERSEDED_AREA_CODES` 에 `12 to setOf(46, 29)` 를 두고, 통합시가 응답에 있을 때만 구성 지역을 접는다. 서버가 46·29 를 빼고 내려주면 **이 표만 지우면 된다.** 접을 때마다 경고 로그가 남는다.

2층 지도가 생겨도 이 문제는 그대로다. `popular-destinations` 는 areaCode 를 쓰지 않아 무관하지만, **아래층은 여전히 `regions/popularity` 로 칠하기 때문**이다.
아래층을 걷어내기로 하면 이 절 전체가 함께 사라진다.

`4,099,426` 이라는 값 자체가 맞는지는 여전히 미확인이다. 시트에 그대로 노출된다.

### 그 밖에

- 서버가 **좌표를 주지 않아** 시도 17개 좌표를 클라가 상수로 갖고 있다(`SidoAreas.AREAS`). 행정구역이 바뀌면 앱 배포가 필요하다. 이번 `areaCode 12` 가 정확히 그 경우였다. 서버가 좌표까지 내려주면 이 표는 사라진다.
- 모르는 areaCode 가 오면 지도에 놓을 자리가 없어 제외하되 **경고 로그를 남긴다**. 이번에 12번을 못 알아챈 게 로그가 없어서였다.

## 6. 남은 일 / 논의거리

### 연관 콘텐츠 — 2층 지도로 대부분 해결됐다

예전에 적어 둔 세 가지 문제(콘텐츠 없는 시도 10곳 / 정렬 기준 없음 / 버튼이 첫 카테고리로만 이동)는 **전부 사라졌다.**
`1지역 = 1카테고리` 가 되면서 병렬 호출·`distinctBy`·`primaryRegionCategoryName` 이 다 필요 없어졌기 때문이다.

- 콘텐츠 조회는 **위층을 탭했을 때만**, 호출은 언제나 한 번이다.
- 아래층 시도(경기·충북 등)를 누르면 방문자 수만 보여 준다. 콘텐츠가 붙는 건 위층뿐이다.
- `size = 10`, 페이징 없음. 지역별 캐시는 그대로.
- `SidoAreas.AREA_CODES_BY_REGION_CATEGORY` 는 이제 쓰이지 않는다. 지울 수 있다.

### 바텀시트

`f7e5ea643` 에서 세 가지를 고쳤다.

- 지도가 밀리는 양을 별도 애니메이션에서 **시트의 실제 위치(`requireOffset()`) 계산**으로 변경. 애니메이션 두 개가 각자 돌아 어긋나던 것이 원인이었다. 덤으로 손으로 시트를 끌 때도 지도가 따라온다.
- 선택을 풀면 본문이 즉시 사라져 **빈 흰 시트가 내려가던** 문제 → `lastShownRegion` 으로 닫힐 때까지 유지
- 지역 전환 시 `AnimatedContent`(220ms), 콘텐츠 로딩 후 높이 점프는 `animateContentSize`

**아직 실기기에서 눈으로 확인하지 않았다.** 220ms 와 슬라이드 거리(시트 높이의 1/6)는 `PopularRegionScreen.kt` 아래쪽 상수로 빼 두었으니 조절하면 된다.

시트가 올라오는 속도 자체는 Material3 내부 스펙이라 공개 API 로 못 바꾼다. 손대려면 `BottomSheetScaffold` 를 직접 만든 시트로 교체해야 한다.

### 그 외

- 기준월이 `202608` 이라 화면에는 **2026년 8월**로 표시된다. 스펙 문서 예시(`202506`)와 다르니 헷갈리지 말 것.
  두 API 의 `baseMonth` 가 서로 다를 수 있는데 지금은 **시도 쪽 값만** 화면에 쓴다.
- **라벨이 겹칠 자리가 늘었다.** 세종-대전(12dp)에 더해 수원-서울, 공주-대전, 강릉-속초가 가깝다.
  위층을 먼저 배치해 겹치면 관광지가 이기도록 해 뒀지만, 실기기 확인이 필요하다.
- **진한 빨강 위의 라벨이 잘 안 읽힌다.** `Label`(#4A4A4A) 대 `HeatHigh`(#E23B3B) 대비가 2.2:1 이다.
  1·2위 지역에서 특히 그렇다. 2층 이전부터 있던 문제이긴 하나, 관광지 도형이 작아 더 눈에 띈다.
- `rank` 는 받아만 두고 1위 배지(`인기 지역`)에만 쓴다. 2~10위를 지도나 시트에 적을지는 미정.
